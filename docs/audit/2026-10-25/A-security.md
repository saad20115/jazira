## Findings

### A-01 [major · confirmed] The JSON-LD on every public page is serialized without escaping `<` (I2)
- Where: `src/app/(frontend)/[locale]/layout.tsx:111-123` (builder) and `:258-263` (sink).
- Code: `return JSON.stringify({ '@context': 'https://schema.org', '@type': 'Organization', name: siteSettings?.companyName || …` → `dangerouslySetInnerHTML={{ __html: buildOrganizationJsonLd(…) }}`
- Problem: I2 allows `dangerouslySetInnerHTML` only for JSON-LD "built from a serializer that escapes `<`". `JSON.stringify` does not escape `<`, `>`, `&` or U+2028/2029. `companyName` is CMS text (max 200), so a value such as `</script><meta http-equiv="refresh" content="0;url=https://evil.example">` breaks out of the script element. The task card for the proper JSON-LD (`handoff/tasks/P3-T10.md:10`) requires the escaping, but this earlier copy (commit f52b25d, P3-T12) shipped without it. The P3-T12 review checked only the locale.
- Impact: stored HTML injection into the `<body>` of every page, in both locales. The nonce plus `strict-dynamic` CSP blocks injected `<script>` and inline handlers, but it does not block markup such as a meta-refresh redirect, a phishing form posting to `'self'`, or link spoofing. Only an admin can write the field (`SiteSettings.ts:382-384`), so the threat is a compromised admin account. A7 (no 2FA) leaves that path open.
- Fix / refactor: add one `serializeJsonLd(obj)` helper in `src/lib`: `JSON.stringify(obj).replace(/</g,'\\u003c').replace(/>/g,'\\u003e').replace(/&/g,'\\u0026').replace(/\u2028/g,'\\u2028').replace(/\u2029/g,'\\u2029')`. Use it here and in P3-T10. Add a unit test with `</script>` in `companyName`.

### A-02 [major · confirmed (source-traced; runtime check recommended)] Media and video uploads can skip every project upload control through a JSON `{url, filename}` create
- Where: `src/collections/Media.ts:34-40`, `src/collections/Videos.ts:58-87` (the validators run only `if (req.file)`), and `Videos.ts:97-157` (the size and part limits apply only to multipart bodies). Payload 3.91: `collections/operations/create.js:34-35` (`if (upload && !overrideAccess) externalUploadSource = getExternalUploadSource(args.data)`), `uploads/generateFileData.js:66-88`, `uploads/getExternalFile.js:82,107` (`res = await safeFetch(fileURL…)` … `const data = await res.arrayBuffer()`).
- Code: `if ((operation === 'create' || operation === 'update') && req.file) { await validateAndSanitizeMediaFile(req.file) }`
- Problem: Payload 3.91 lets any caller with `create` access post `{"url":"https://host/x.mp4","filename":"x.mp4",…}` as JSON. The server then fetches the remote file itself. That file never appears as `req.file`, so the magic-byte check, the 10 MB / 100 MB limits (I5, `02-content-model.md` media/videos), the filename sanitizer and the video endpoint's `fileSize`/`files` limits are all skipped. `getExternalFile` buffers the whole body with no size cap. Its reported size comes from the attacker's `content-length`. Payload's own `checkFileRestrictions` (file-type sniffing against `mimeTypes`) still applies, and `safeFetch` blocks private IP ranges.
- Impact: an editor session, or a stolen one, can make the server download arbitrarily large public resources into memory (memory/DoS) and store over-limit videos. It also turns the server into an outbound fetcher of public URLs. This contradicts the I5 size limits, and Nginx `client_max_body_size` (H6) does not help because the transfer is outbound.
- Fix / refactor: in both `beforeOperation` hooks, throw a `ValidationError` on create/update when `!req.file` and `args.data` has `url` (or `filename`). `create.js` captures `externalUploadSource` before hooks run, so the hook must reject, not strip. Also set `upload.pasteURL: false` on both collections. Add an integration test: editor `POST /api/videos` with a JSON `{url, filename}` body → 400.
- Runtime check: as an editor, `POST /api/media` with JSON `{"alt":"x","filename":"a.jpg","url":"https://<public host>/big.jpg"}`, and confirm whether the server fetches it.

### A-03 [major · confirmed] Committed test and evidence tooling registers the first admin and tries logins with passwords that are public in git, against whatever base URL it is given
- Where: `tests/e2e/global-setup.ts:3-21` (`E2E_ADMIN_PASSWORD = 'Stro…'`, `POST ${baseURL}/api/users/first-register`, then tries logins with three hard-coded admin credentials). `playwright.config.ts:25` (`baseURL = process.env.SERVER_URL ?? …`). `scripts/evidence/p3-t12-evidence.mjs:17-20,82-95`, `p3-t13-evidence.mjs:41,53`, `p3-t4-evidence.mjs:92,105` (fallback `'Pass…'`, also `first-register`).
- Code: `await fetch(\`${baseURL}/api/users/first-register\`, { method: 'POST', … password: E2E_ADMIN_PASSWORD })`
- Problem: the target comes from `SERVER_URL`, the same variable that holds the production origin in the app's `.env`. Nothing checks that it is loopback. On a freshly deployed, empty production DB, one `pnpm test:e2e` or evidence run creates the site's first **admin** with a password that is in the public git history. On a populated DB it runs a login loop against real accounts, which counts toward A1 lockouts. This is the same class of unscoped side effect as the `Stop-Process node` incident.
- Impact: risk of a full admin takeover during the deployment window (Phase 6), and of locking out real staff.
- Fix / refactor: one shared `assertLocalTestTarget(url)` that refuses anything other than `localhost`, `127.0.0.1` or `[::1]` (or an explicit `ALLOW_REMOTE_TEST_TARGET=1`). Generate per-run random credentials and write them to an ignored file. Remove the hard-coded password fallbacks. Never call `first-register` from tooling except against loopback.

### A-04 [minor · confirmed] A second `dangerouslySetInnerHTML`, for a non-JSON-LD inline script, is not declared as a deviation (I2)
- Where: `src/app/(frontend)/[locale]/layout.tsx:408-411`, script body `src/components/IntroSplash.tsx:35`.
- Code: `<script nonce={cspNonce} dangerouslySetInnerHTML={{ __html: INTRO_PREPAINT_INLINE_SCRIPT }} />`
- Problem: I2 says "No `dangerouslySetInnerHTML` anywhere except the JSON-LD". The content is a static constant and carries a nonce, so XSS risk is low. It is still a spec breach that the reports present as H3-compliant (`handoff/reports/P3-T4.md:222`) and never list under Deviations.
- Impact: low today. It is precedent for further raw-HTML sinks, and the I2 audit trail is wrong.
- Fix / refactor: move it to a static `public/intro-prepaint.js` loaded with `<script src nonce>` (`strict-dynamic` already trusts it), or get a recorded CTO waiver. Add an ESLint `react/no-danger` rule with a single allow-listed JSON-LD helper.

### A-05 [minor · confirmed] `projects.reviewNote` is staff-wide, but the spec says admin-only
- Where: `src/collections/Projects.ts:1185-1195` (also `needsClientReview` at `:1163-1172`).

### A-06 [minor · confirmed] Payload job endpoints fall back to "any logged-in user"; the Z1 test skips them
- Where: `src/payload.config.ts:117-126` (no `jobs.access`); `src/access/z1-config-enumeration.test.ts:30-36` (skips `payload-jobs`). Payload: `queues/endpoints/run.js:17` and `handleSchedules.js:18` (`jobsConfig.access?.run ?? defaultAccess`, where `defaultAccess = Boolean(user)`).
- Problem: Z1 asks for explicit access everywhere. With `schedulePublish: true` the jobs collection and its `/api/payload-jobs/run` and `/handle-schedules` endpoints exist, and any editor may call them. The collection's own CRUD is `() => false` (good).
- Impact: low. An editor can trigger queue processing or scheduling runs on demand (load). Only jobs that are already due run.
- Fix / refactor: `jobs: { access: { run: isAdmin, queue: isAdmin, cancel: isAdmin } }` (check that the `autoRun` cron is unaffected; it calls `runJobs` internally). Extend the Z1 test to assert `config.jobs.access.*` are explicit.

### A-07 [minor · suspected] The admin CSP relaxations are asserted, not verified, and one of them leaks staff email hashes to a third party
- Where: `src/security/csp.ts:336-400`.
- Code: `"script-src 'self' 'unsafe-inline' 'unsafe-eval'"`, `"img-src 'self' data: blob: https://www.gravatar.com"`
- Problem: H3 allows relaxations "scoped to `/admin` and documented". The scoping is correct (`isAdminRoutePath`, `proxy.ts:143-176`). However, `'unsafe-inline' 'unsafe-eval'` together remove essentially all XSS protection in the most privileged UI. The proxy already generates and forwards `x-nonce` for `/admin` (`proxy.ts:146`), so a nonce-based admin policy is probably possible. `'unsafe-eval'` is typically needed only in dev. The Gravatar relaxation exists because Payload's default `admin.avatar` is `'gravatar'` (`payload/dist/config/defaults.js:8`). Each admin page view sends the MD5 of a staff email to gravatar.com (a D2/PDPL privacy concern).
- Impact: a stored XSS in any admin-rendered field would run unhindered in an admin session.
- Fix / refactor: set `admin.avatar: 'default'` and drop the Gravatar source. On a production build (`next start`), try `script-src 'self' 'nonce-…' 'strict-dynamic'` and then drop only `'unsafe-eval'`. Keep a relaxation only if the admin console shows a violation, and record that evidence.
- Runtime check: production build, admin CSP without `'unsafe-eval'`, then exercise the list view, the edit view with Lexical, upload crop and live preview, and capture any `securitypolicyviolation` events.

### A-08 [minor · confirmed] Secret validation checks length, not strength; the DB role is not checked (S1, S2, D1)
- Where: `src/env.ts:39-52`, `:94-104`.
- Code: `.min(48, \`${varName} must be at least 48 characters long…\`)` plus a placeholder-substring refine.
- Problem: S2 requires ≥ 48 random **bytes** (`openssl rand -base64 48` = 64 characters), and S1 says boot must fail when a secret is "weak". `'a'.repeat(48)` passes. `DATABASE_URL` is accepted with the `postgres` superuser, although D1 says the app must not connect as `postgres`.
- Impact: a weak `PAYLOAD_SECRET` (JWT signing, the preview HMAC) or a weak `IP_HASH_SALT` can reach production without any warning.
- Fix / refactor: require ≥ 64 characters, or base64-decode and require ≥ 48 bytes, and reject low-diversity values (e.g. < 16 distinct characters). In production, reject `postgres://postgres:` / user `postgres`. Add unit cases.

### A-09 [minor · confirmed] The email transport is hard-wired to plaintext with no auth and falls back silently, so forgot-password (A5) can fail without any error
- Where: `src/security/emailAdapter.ts:9-24` (and the non-blocking wrapper at `:28-44`).
- Code: `host: process.env.SMTP_HOST ?? '127.0.0.1', port: Number(process.env.SMTP_PORT ?? '1025'), pool: true, secure: false` … `skipVerify: true`
- Problem: the SMTP settings bypass the zod env validation (S1), there is no `auth` and no TLS option, and an unset host silently means `127.0.0.1:1025`. The wrapper always resolves `{queued: true}` and only logs a code. That is deliberate (it keeps A5 response timing uniform), but it hides the misconfiguration.
- Impact: if production starts without SMTP variables, password resets look successful but no email is ever sent. A real relay would also need `requireTLS`/`auth`, which the adapter cannot accept.
- Fix / refactor: move the SMTP variables into `env.ts`, required in production, with `SMTP_SECURE`/`SMTP_USER`/`SMTP_PASS`. Pass `auth` and `requireTLS: true` through. Keep `skipVerify: false` in production, or log a single boot-time verify result. Track this under Phase 5 S1.

### A-10 [minor · confirmed] Uploaded-file responses carry no CSP or sandbox
- Where: `src/proxy.ts:246-249` (the matcher excludes `api`); `next.config.ts:64-88` (no extra headers for file routes).
- Problem: `/api/media/file/*` and `/api/videos/file/*` serve user-supplied bytes with only `nosniff` and `X-Frame-Options`. Media is re-encoded to WebP (`Media.ts:590-592`), which neutralizes polyglots. Videos are stored byte-for-byte (`Videos.ts:243-247`).
- Impact: low, defence in depth only. A mis-sniffed or future file type would render with the site origin's privileges.
- Fix / refactor: in `next.config.ts` `headers()`, add `Content-Security-Policy: default-src 'none'; media-src 'self'; sandbox` for `/api/:col(media|videos)/file/:path*`.

### A-11 [nit · confirmed] The user `afterRead` strip fails open for anonymous callers
- Where: `src/collections/Users.ts:215-218`.
- Code: `if (!caller || caller.role === 'admin') { return record }`
- Problem: the defense-in-depth hook returns the full user record when there is no `req.user`. It is unreachable through REST today (collection `read: isAdminOrEditor`, and field-level `read` still hides `email`/`role`). Any future public relationship to `users` would then depend on one layer only.
- Fix / refactor: for a missing caller, return `{ id, name }` (or nothing).

## Refactor themes (max 6)
- **One output-encoding layer.** Files: `layout.tsx`, a future `src/lib/jsonLd.ts`, `IntroSplash.tsx`. Benefit: a single tested JSON-LD serializer, zero raw-HTML sinks, and an ESLint `react/no-danger` rule with a one-file allowlist. Risk: low.
- **Upload intake through one gate.** Files: `Media.ts`, `Videos.ts`, `uploadValidation.ts`. Benefit: reject non-multipart (URL/paste) sources, apply size and magic checks in one `beforeOperation` factory, and drop the duplicated endpoint-wrapping in `Videos.ts`. Risk: medium (the admin "paste URL" UX disappears; it should be confirmed unused).
- **Config-driven access map plus an exhaustive Z1 test.** Files: `src/access/*`, `payload.config.ts` (`jobs.access`), `z1-config-enumeration.test.ts`. Benefit: one table of role × operation per collection, global, field and job endpoint, with the test generated from it, so drift like A-05 and A-06 cannot pass. Risk: low.
- **Typed env for all runtime config.** Files: `env.ts`, `emailAdapter.ts`, `layout.tsx` and `client.ts` (`process.env.SERVER_URL`/`NEXT_PUBLIC_SERVER_URL` read directly). Benefit: entropy checks, required SMTP and TLS in production, a single `SERVER_URL` source. Risk: low; the build-phase fallback must stay.
- **Safe test and evidence harness.** Files: `tests/e2e/global-setup.ts`, `scripts/evidence/*`, `playwright.config.ts`. Benefit: a loopback-only target guard, random per-run credentials, no `first-register` against remote hosts. Risk: low.
- **Admin CSP tightening.** Files: `security/csp.ts`, `payload.config.ts` (`admin.avatar`). Benefit: a nonce-based admin policy with no Gravatar. Risk: medium; needs a production-build check of the Payload admin.
