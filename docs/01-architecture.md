# 01 — Architecture & decisions

Status: **approved by CTO, 2026-10-21.** Changing anything here requires a written question in a
phase report and CTO approval.

## 1. What we are building
A bilingual (English default / Arabic RTL, switchable on by an admin) marketing website for **Al Jazira for Imdad Smart Co.**
(MEP contractor, Makkah, KSA), with a dashboard where non-technical staff manage all content:
projects, services, team, brands, approved materials, media (images, video), contact details,
and home-page sections. Quote requests from the site are stored in the dashboard and emailed to the
sales inbox. **No Odoo integration** (owner decision 2026-10-23, see §5).

Pages (from the approved Figma design): Home, Services, About, Projects, Project detail, Contact.

## 3. Application shape
- **One Next.js app** containing both the public site (`src/app/(frontend)`) and Payload admin +
  API (`src/app/(payload)`), as generated by the official template.
- Payload **Local API** for all server-side data fetching in the frontend (no HTTP round-trips to
  itself). REST API stays enabled for the admin. **GraphQL is disabled** (`graphQL.disable: true`)
  — we don't use it, so it is attack surface we remove.
- Rendering: static/ISR for public pages, revalidated on content change via Payload `afterChange`
  / `afterDelete` hooks calling `revalidateTag` / `revalidatePath`. Drafts + **Live Preview** for
  editors.
- Localization: Payload `localization` with locales `en` (**default**) and `ar` (`rtl: true`),
  `fallback: true`. URLs: `/en/...` and `/ar/...`; `/` redirects to `/en`.
- **Arabic switch (owner decision 2026-10-24):** `site-settings.arabicEnabled` (checkbox, default
  **off**, admin-only update).
  - **Off:** `/ar/*` answers with a temporary 307 redirect to the same `/en/*` path. The language
    switcher is hidden. `hreflang` lists `en` + `x-default` (`/en`) only. The sitemap has `en` URLs
    only.
  - **On:** today's bilingual behaviour, with `ar` in `hreflang` and the sitemap and the switcher shown.
  - Saving the setting revalidates the public cache, so the change is live without a redeploy.
  - The flag is read through a cached call, never one DB query per request.
  - Arabic content is still written and reviewed. Every task still builds and tests `ar` with the
    flag on, so switching it on later is safe.
- Admin UI language: English by default, Arabic available per user (`@payloadcms/translations` `en`, `ar`).
- Next.js 16 note: request interception lives in **`proxy.ts`** (formerly `middleware.ts`).
- `next.config`: `output: 'standalone'`, `poweredByHeader: false`, `images.remotePatterns` limited
  to our own domain only.

## 4. Infrastructure (production — built in Phase 6 only)
The client's **Hostinger VPS already runs an Odoo website in production.** Rule #1: we must not
disturb it.

```
Internet ──443──> Nginx (host) ──┬── aljazira.co, www  → 127.0.0.1:3000  (Next.js + Payload, Docker)
                                 └── erp./odoo. domain → existing Odoo (unchanged)
Docker network "aljazira_web" (internal):  web (Next/Payload, non-root)  ⇄  db (Postgres 18)
```

Decisions:
- **Separate Postgres container for the website** (not a new DB inside Odoo's Postgres). Reason:
  isolation — a bug, migration, or compromise on the website cannot touch Odoo data, and Odoo
  upgrades can't break the website. Cost: ~100–150 MB RAM. DB port is **not** published to the host.
- Website runs in Docker (`web` + `db` via docker compose), app container as non-root, read-only
  root filesystem except the media volume and `/tmp`.
- Nginx on the host terminates TLS (Let's Encrypt, auto-renew), proxies only to `127.0.0.1:3000`.
- Media files: persistent Docker volume `media`, included in backups. (S3/R2 adapter can be added
  later without changing the content model.)
- Videos: editors can either upload short MP4/WebM clips (size-limited) or paste a YouTube/Vimeo
  URL. Long videos must use the URL — VPS bandwidth is limited.
- Backups: nightly `pg_dump` of the website DB + tar of the media volume, 14 daily / 8 weekly
  retained, copied off-server. Restore procedure is tested in Phase 6.
- Before ANY change on the VPS: full backup of Odoo DB + filestore + `odoo.conf` + Nginx config.

## 5. Quote requests (Phase 5) — Odoo integration REMOVED (owner decision 2026-10-23)
The owner does not need the website connected to Odoo. Quote requests are **saved in Payload**,
handled by staff in the dashboard (status workflow, notes, CSV export), and announced to the sales
inbox by email from a **Payload Jobs** task with retries. The Odoo text below is kept only as
history; do not implement it. Odoo still runs on the same VPS, so all "do not touch Odoo" rules
for deployment (§4, Phase 6) stay in force.

### (superseded) Odoo integration
- Direction: website → Odoo only. A quote request creates a `crm.lead`.
- Auth: a **dedicated Odoo user** ("Website Integration") with the minimum rights needed to create
  leads, and an **API key** for that user. Never an admin account. Key lives only in server env.
- Protocol depends on the client's Odoo version (to be confirmed):
  - Odoo 19+: JSON-2 API — `POST /json/2/crm.lead/create` with `Authorization: bearer <api key>`.
  - Odoo ≤ 18: JSON-RPC `/jsonrpc`, `object.execute_kw` with the API key as password.
  The client code sits behind one small interface (`createLead(input)`) so the protocol can change.
- Reliability: the quote is **saved in Payload first**, then pushed by a **Payload Jobs queue** task
  with retries/backoff. Status on the record: `pending → sent | failed`, with `odooLeadId` and the
  last error (sanitized). A failed push never loses the request and never shows the visitor an
  error after the save succeeded.
- Optional: email notification to the sales inbox via SMTP (nodemailer adapter).
