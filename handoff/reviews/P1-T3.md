## Round 1 — 2026-10-21 — CHANGES_REQUESTED
Strong work: role escalation, lockout, logout revocation and the upload content checks all hold
up under my own attacks (details under Verified). Four issues block acceptance — three are
security/operations gaps the tests did not cover, one is a report/code mismatch.

### Findings
- R-1 [major] **Forgot-password leaks which emails exist through timing (A5).** Bodies are
  identical (`{"message":"النجاح"}`, 200), but a known email took **1.20 s** and an unknown one
  **0.03 s** — the request waits for the SMTP send only when the user exists. That is user
  enumeration. Fixed = both paths indistinguishable: send the email without making the response
  wait (e.g. Payload Jobs task or a non-awaited send with error logging by user ID), or pad to a
  fixed minimum duration. Test: 20 requests each for known/unknown email, report the median and
  max of both; the difference of medians must be < 100 ms. Email still arrives (Mailpit proof).
- R-2 [major] **The last admin can be deleted or demoted.** As the only admin I ran
  `DELETE /api/users/1` → **200**, leaving **0 admins** and 1 editor. First-register is then
  closed (a user exists), so nobody can ever manage users again without DB access. Fixed =
  `beforeDelete` and `beforeChange` guards: refuse deleting the last admin and changing the last
  admin's role to `editor` (clear Arabic/English message), with integration tests for both.
- R-3 [major] **Admin "revoke sessions" writes arbitrary data.** `Users.ts` stashes any
  `sessions` array an admin sends and writes it with `payload.db.updateOne` in `afterChange`,
  bypassing validation. I injected `{"id":"fabricated-by-admin","expiresAt":"2099-01-01"}` and it
  was stored as-is. The goal (A2) is only "admin can force-logout a user". Fixed = remove the
  `sessions` passthrough; add a dedicated admin-only endpoint
  `POST /api/users/:id/revoke-sessions` (custom collection endpoint, access checked inside) that
  only **clears** the sessions; test: editor → 403, admin → 200 and the user's old token then gets
  `user: null` from `/api/users/me`. A button in the admin edit view can come in P2-T7.
- R-4 [major] **Media location: report and code disagree, and the path will break in
  production.** The report says files are stored in `storage/media`; the code is
  `path.resolve(dirname, '../../media')` (repo-root `media/`) with `dirname` from
  `import.meta.url`. In bundled output (standalone/Docker) that resolves relative to the compiled
  chunk, not the project, and in dev every upload makes Turbopack rebuild ("frequent file
  updates" in the log). Fixed = `MEDIA_DIR` env var (absolute path, validated in `src/env.ts`,
  default `<cwd>/media` in dev, `.env.example` documented), `staticDir` reads it, Turbopack/
  watcher ignores it, and the report states the real location. Prove upload + `GET` of the file
  still work.
- R-5 [minor] Message numbering: your submission reused **M-016** (I had posted M-016 at 14:31).
  Before appending, read the last `## M-` number and use the next one.
- R-6 [minor] `Users.ts` / `Media.ts` hooks use `hookArg as unknown as {…}` casts. Use Payload's
  hook types (`CollectionBeforeOperationHook`, `CollectionBeforeValidateHook`, …) so the
  compiler checks them. Can be done with the R-1…R-3 changes.
