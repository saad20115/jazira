### 7. Admin language behaviour with `Accept-Language: en-US` and `ar` (Scope §5)
Inspection of `node_modules/payload/dist/utilities/getRequestLanguage.js`:
```js
export const getRequestLanguage = ({ config, cookies, headers }) => {
  const supportedLanguageKeys = Object.keys(config.i18n.supportedLanguages);
  const langCookie = cookies.get(`${config.cookiePrefix || 'payload'}-lng`);
  const languageFromCookie = typeof langCookie === 'string' ? langCookie : langCookie?.value;
  if (languageFromCookie && supportedLanguageKeys.includes(languageFromCookie)) {
    return languageFromCookie;
  }
  const languageFromHeader = headers.get('Accept-Language')
    ? extractHeaderLanguage(headers.get('Accept-Language'))
    : undefined;
  if (languageFromHeader && supportedLanguageKeys.includes(languageFromHeader)) {
    return languageFromHeader;
  }
  return config.i18n.fallbackLanguage;
};
```

## Questions for CTO
1. **S4 (`import 'server-only'`) vs Payload CLI (`generate:types`, `migrate`)**:
   As verified in Evidence §6, `server-only` throws `Error: This module cannot be imported from a Client Component module` whenever `payload.config.ts` (and therefore `src/env.ts`) is loaded by the Payload CLI (`tsx` / Node without `--conditions react-server`) or Vitest.
   **Proposed S4 replacement**:
   - In `eslint.config.mjs`, enforce `no-restricted-imports` on all client/frontend component paths (`src/components/**`, `src/app/(frontend)/**/*.client.tsx`) forbidding imports of `@/env`, `./env`, `@/lib/odoo/**`, and `@payload-config`.
   - In CI (P1-T4) and Phase 5, run a build-time verification step that greps `.next/static` for secret variable names/prefixes (`PAYLOAD_SECRET`, `IP_HASH_SALT`, `DATABASE_URL`, `ODOO_API_KEY`) and fails if any match is found.
   - Alternatively, if you also want `server-only` at runtime, we can pass `--conditions=react-server` inside `NODE_OPTIONS` on the `payload`, `generate:types`, and `generate:importmap` scripts in `package.json`. Please confirm which approach you prefer.
2. **Admin UI initial language when browser sends `Accept-Language: en-US` (Scope §5)**:
   As shown in Evidence §7 (`node_modules/payload/dist/utilities/getRequestLanguage.js`), Payload 3.91 checks `cookies.get('payload-lng')` first, then `headers.get('Accept-Language')` against `supportedLanguages` (`{ ar, en }`), and only uses `fallbackLanguage: 'ar'` when neither cookie nor matching `Accept-Language` header is present. Thus, a first visit with `Accept-Language: en-US` opens `/admin` in English (`lang="en" dir="LTR"`), whereas `Accept-Language: ar` (or no `Accept-Language`) opens `/admin` in Arabic (`lang="ar" dir="RTL"`).
   - Should we accept Payload 3.91's built-in `Accept-Language` negotiation for `/admin` (where Playwright e2e in P1-T4 sets `locale: 'ar'` or tests without `en-US` first, then switches to `en`), **or** should we set the default `payload-lng=ar` cookie on first visit to `/admin` when no `payload-lng` cookie is present?
