## Review findings
- **R-1 [major]**: Added `src/instrumentation.ts` whose `register()` runs on the Node runtime (`process.env.NEXT_RUNTIME === 'nodejs'`), imports `parseEnv` from `./env`, validates `process.env`, writes the error message (with no secret values) to `stderr`, and calls `process.exit(1)`. To ensure `next build` does not require production secrets at Docker build time, `src/env.ts` (`loadEnv()`) and `src/instrumentation.ts` check `process.env.NEXT_PHASE === 'phase-production-build'`: during `next build` only, unset env vars fall back to build-only ephemeral values so standalone compilation succeeds, while at server boot (`next dev` and `node .next/standalone/server.js`) `NEXT_PHASE` is unset and `register()` exits with code `1` before serving (proven in Evidence §2 below).
- **R-2 [minor]**: Removed fixed `container_name: aljazira-dev-db` and volume `name: aljazira_pgdata` from `docker-compose.dev.yml` and set top-level `name: aljazira` so containers and volumes are project-scoped (`aljazira-db-1`, `aljazira_aljazira_pgdata` — Evidence §1).
- **R-3 [answer to Q1]**:
  1. Added a documentation comment at the top of `src/env.ts` explaining why it is the exception to `import 'server-only'` (imported by `src/payload.config.ts` under the Payload CLI). All server modules not reachable from `src/payload.config.ts` will keep `import 'server-only'`.
  2. Implemented the in-repo ESLint rule `local/no-server-in-client` (`eslint-rules/no-server-in-client.mjs`), enabled as `'error'` in `eslint.config.mjs`, forbidding imports of `@/env`, `@payload-config`, `@/payload.config`, `payload`, `@/lib/odoo/**`, `@/lib/ipHash`, or any `*.server.ts(x)` inside files starting with `'use client'`. Added `src/eslint-no-server-in-client.test.ts` proving the rule flags all 7 forbidden imports in a `'use client'` file and reports 0 errors on a server file (Evidence §6).
- **R-4 [answer to Q2]**: Created `src/proxy.ts` (`matcher: ['/admin', '/admin/:path*']`) which checks `request.cookies.has('payload-lng')`. Only when absent, it sets `payload-lng=ar` on both the forwarded request headers (so the very first `/admin` response renders in Arabic RTL) and the response cookie (`path: '/'`, `maxAge: 31536000`, `httpOnly: false`, matching Payload's `switchLanguageServerAction` in `@payloadcms/next/dist/layouts/Root/index.js`). Verified in Playwright (Evidence §7 and screenshots `docs/reports/phase-1/admin-accept-lang-en-US.png` and `docs/reports/phase-1/admin-account-switched-en.png`) that a fresh `Accept-Language: en-US` browser opens `/admin` in Arabic RTL (`lang="ar" dir="RTL"`), and switching to English in `/admin/account` persists (`lang="en" dir="LTR"`) across page reload and in a new tab.
